1The idea

ForgeOne is an agent that builds agents. You give it a goal in plain language, such as "build a web discovery agent that researches a question and writes a sourced report", and it designs, writes and (from Day 2) tests and repairs that agent on its own. The first agent it builds is VoyagerOne: an autonomous researcher that searches the web, reads pages, cross-checks facts across sources and writes a report listing the URLs it actually read.

The core design choice is that ForgeOne does not write code. It writes a spec: a structured description of the agent (its system prompt, the tools it may use, its step budget and its test cases). A small, fixed runtime turns a spec into a running agent. This keeps every generated agent checkable, diffable and safe: ForgeOne can only choose from tools we wrote and approved, and every version of every agent can be compared line by line.

2The decisions, and why

Framework: LangGraph for the builder

We compared writing everything from scratch, lightweight SDKs (Pydantic AI, OpenAI Agents SDK, Claude Agent SDK) and full frameworks (LangGraph, CrewAI, AutoGen). We chose LangGraph for the builder because its strengths match the builder's job:

  • Cycles: the builder's main loop is plan, build, test, judge, then back to build. LangGraph models that loop directly, with conditional edges.
  • Checkpointing: a long autonomous build that crashes on iteration 7 can resume from its last checkpoint instead of starting over.
  • Interrupts: it can pause for human approval before something important happens.

The agents ForgeOne generates are not LangGraph code; they are specs. Asking a model to write correct graph code (state schemas, reducers, edges) fails far more often than asking it to fill in a well-defined form, and it would tie every generated agent to LangGraph's API.

Browser: Playwright first, AI browser tools later

Chromium is the browser itself; Playwright, Stagehand and Browser Use are all ways of driving it. The real question is who decides each click:

OptionWho decidesTrade-off
PlaywrightOur agent; tools are plain codeNo extra model cost, fully visible in our logs, fails on very interactive sites
StagehandOur agent says what; Stagehand works out howOne model call per action, good control
Browser UseIts own agent decides everythingPowerful, but a black box inside our agent: two brains, double cost, harder to debug

Decision: VoyagerOne's basic tools (search, open, click, find, write report) use Playwright. Later we add one fallback tool backed by Browser Use for interactive pages, and the builder decides when an agent gets it. The reason is the feedback loop: the builder can only repair what it can see, and Playwright steps show up in our traces one by one.

Repositories

We started with the idea of two repositories, one for the builder and one per generated agent. For now everything lives in one repo, ForgeOne. VoyagerOne will get its own repository once it runs on its own; ForgeOne will then publish each new version there as a pull request, so merging becomes your approval.

Model: Haiku 5.5 by default

The first builds ran on Sonnet 5.5 and cost about 5 cents each. We switched the default to Claude Haiku 5.5, which costs $0.10 per million input tokens and $0.50 per million output tokens for prompts up to 100,000 tokens, against $2 and $10 for Sonnet 5.5. One build now costs about a third of a cent. The model can be overridden per run with FORGEONE_MODEL=claude-sonnet-5-5, which matters later: you may want a stronger model to judge than to build.

Two API details we learned

  • No custom temperature on the newest models: passing temperature=0.2 raises an error, so we leave it at the default.
  • Structured output uses method="json_schema". The older default (forced tool calling) is not supported on these models and can fail at random with an OutputParserException.

4The builder graph

A LangGraph program has three building blocks:

  • State: a typed dictionary every step can read (ForgeState with goal, plan, spec).
  • Nodes: plain Python functions. A node receives the state and returns only the keys it changes, for example {"plan": "..."}. LangGraph merges that update into the state.
  • Edges: the order of the nodes. Normal edges always go to the next node; conditional edges choose the next node from the state, which is how loops are built.

plan asks Claude for a build plan in free text: scope, which tools and why, the research method, the stopping rule, the report format and test tasks. build turns the plan into a validated AgentSpec using structured output. If the model returns something that does not fit the schema, the call fails instead of silently producing a broken agent.

Run it with python -m forgeone.graph. It reads goals/voyagerone.md and writes the spec to runs/<run_id>/spec.yaml and to the database.

5The AgentSpec contract

The spec is the boundary between "what the builder may decide" and "what we control". It is a Pydantic model in forgeone/spec.py:

FieldMeaningRule
nameIdentifier, e.g. voyageronekebab-case
descriptionOne paragraph about the agent
system_promptThe agent's entire "brain": role, method, source rules, stopping rule, report formatthe most important field
toolsWhich tools the agent may callonly from the catalog, enforced by Literal
max_stepsMaximum tool calls per task5 to 60
test_casesTasks with checkable success criteria2 to 4

The tool catalog is web_search, open_page, click, find_on_page and write_report. Because tools is typed as a list of those exact names, the model cannot invent a tool: the schema itself rejects it. This allowlist is the main safety boundary of the whole system.

The first spec ForgeOne produced already showed good instincts: a rule that every fact must trace to a page opened in the same run, labels for facts (Confirmed, Single-source, Conflicting), and a test asking about a study that does not exist, the "Hartwell-Okafor Study", to check that VoyagerOne refuses to make things up. That trap test is exactly the kind of evaluation chapter 12 is about.

6Observability

You cannot improve an agent you cannot see. forgeone/observability.py turns every run into a stream of structured events, each one a single JSON object.

The event types

EventWhenKey fields
run.start, run.end, run.errorOnce per rungoal, model, status, duration
node.start, node.end, node.errorAround every graph stepinput and output summary, duration, traceback
llm.request, llm.response, llm.errorEvery model callmodel, latency, input and output tokens, stop reason, payload files
decisionWhen ForgeOne chooses somethingwhat it chose, why, details
artifactWhen a run produces somethingkind (spec, report, verdict), name, full body

The mechanisms worth understanding

  • Correlation without passing IDs around. run_id, node and iteration live in Python ContextVars. start_run() sets the run, @traced_node sets the node, and every event picks them up automatically.
  • Automatic model-call logging. LLMCallLogger is a LangChain callback handler passed once in the graph config. It sees every model call in every node, so nobody has to remember to log one.
  • Small lines, big payloads. Full prompts and answers go to payloads/*.json files and to the database, never into the event line itself. Large data travels to Postgres as "blobs" that the file log skips.
  • Redaction. Strings that look like API keys, tokens or passwords are replaced with [REDACTED] before anything is written. The redaction runs on values, not on finished JSON, after a test showed that redacting JSON text can corrupt it.
  • Errors are logged, then re-raised. A failing node is recorded with its traceback, but the error still stops the run. Nothing is swallowed.
  • Every event has an event_id, which makes writing it to the database idempotent (see the next chapter).

7The event store

forgeone/store.py mirrors every event into Postgres so the dashboard can query it. The design rules:

  • Non-blocking: PostgresSink is a logging handler that puts events on a queue. A background thread writes them in batches of up to 100, every half second.
  • Never fatal: after three failed writes in a row the sink disables itself and prints one warning. The run continues and the JSONL file still has everything.
  • Idempotent: every table has a unique event_id and inserts use ON CONFLICT DO NOTHING. Writing the same event twice is harmless, which is what makes backfill safe to repeat.
  • Totals are recomputed, not incremented: after each batch, a run's call count and token totals are recalculated from llm_calls, so they stay correct even after replays.
  • Built in the caller's thread: the event dictionary is built in the thread that logged it, because only that thread knows the current run and node.

8The Control Room

The first dashboard was built with Streamlit, which was quick but looked generic and could not do drill-down well. It was replaced by a custom app: a small Starlette JSON API (Starlette is the engine FastAPI is built on) and a hand-written single-page interface with no build step.

PageShows
Overviewweekly numbers with change vs last week, builds and spend per day, goals, recent activity, model usage, step performance
Goals, then one goalbuild history strip, spec versions (identical rebuilds folded together), all builds with cost
Buildtimeline per step, model calls, decisions, the spec with a coloured diff against the previous version, raw event log
Model call (side panel)the exact prompt, answer, structured output, tokens and cost
Errorseach failure once, with traceback and a link to its build
Project docsthese documents, readable and as PDF

Goals are identified by a hash of the goal text, so all builds of the same goal group together. Cost is estimated from tokens and the PRICES table in dashboard/server.py; update it when prices change.

Security decisions

  • The app listens on 127.0.0.1 only; nginx is the public entry point.
  • The dashboard is public without a login, by your choice. Anyone with the URL can read goals, prompts and specs. API keys are redacted and the dashboard cannot start anything.
  • Prompts and web pages are untrusted text, so the interface escapes every value before display. A test injected HTML and script into goals, prompts and errors and confirmed nothing executes.
  • Responses carry X-Content-Type-Options: nosniff, X-Frame-Options: DENY and Cache-Control: no-store for API data.
  • Still open: give the dashboard its own read-only database user, so even a bug could never change data.

12The feedback loop

Anyone can generate an agent; a model writes a plausible system prompt in thirty seconds. What separates a good agent factory from a toy is how well it can tell a better agent from a worse one, and why. Every improvement ForgeOne makes is limited by the quality of the signal it learns from. If the evaluation is noisy, the builder optimizes noise. If the evaluation is biased, the builder learns the bias. If the evaluation is good, every build round makes the agent measurably better. This chapter is the plan for making that signal excellent.

12.1 Principle one: the builder must not grade its own homework

Today ForgeOne writes its own test cases. That is useful for quick checks, but dangerous as the main signal: a builder that writes both the agent and its tests will, over time, write tests its agents pass. This is Goodhart's law: when a measure becomes a target, it stops being a good measure.

So we keep two kinds of tests:

  • Builder tests, written by ForgeOne in each spec: fast, cheap feedback during a build.
  • A fixed eval suite, written and owned by you, stored in the repository (planned: evals/voyagerone.yaml). The builder never sees the expected answers. Only this suite decides whether a new version is promoted.

12.2 Principle two: check with code first, judge with models second

Many failures can be detected without any model, and those checks are free, exact and impossible to fool. Because every tool call is logged, we can check the report against what the agent actually did:

Programmatic checkHowCatches
Every cited URL was openedCompare URLs in the report with open_page calls in the traceFabricated sources, the worst failure of a research agent
Quotes exist on the pageSearch the stored page text for each quoted sentenceInvented quotes and numbers
Report formatRequired sections present, Sources list not emptyFormat drift
write_report called exactly onceCount in the traceProcess errors
BudgetSteps, tokens, cost and time below limitsRunaway loops, cost explosions
Trap tasks answered honestlyNonexistent entity: report must say "not found"Hallucination under pressure

Only what code cannot judge goes to a model: is the answer correct, complete and well reasoned?

12.3 Principle three: make the model judge trustworthy

  • A rubric, not a feeling. Score fixed criteria on an anchored scale: what a 1, a 3 and a 5 look like for faithfulness, completeness and reasoning.
  • Evidence required. The judge must quote the transcript or report for every score it gives. A score without evidence is discarded.
  • Pairwise beats absolute. "Is report A or B better for this task?" is far more reliable than "rate this report from 1 to 10". Compare a challenger version with the current champion on the same task.
  • Swap positions. Ask twice with A and B swapped; models prefer whichever comes first. Count only consistent verdicts.
  • Judge with a different, stronger model than the agent. VoyagerOne runs on Haiku; the judge can run on Sonnet, because judging is rare and cheap compared with running.
  • Calibrate against you. Grade 20 to 30 results yourself, then measure how often the judge agrees. Below about 80% agreement, fix the rubric before trusting the judge with any decision.
# planned judge output, one per task and version
verdict:
  faithfulness: 4      # every claim supported by an opened source?
  completeness: 3      # all sub-questions answered?
  reasoning: 4         # conflicts handled, uncertainty stated?
  evidence:
    - "Report claims 10% limit; source WHO page states 'less than 10%'"
  failure_tags: [coverage.missed_subquestion]
  confidence: medium

12.4 Principle four: a balanced scorecard, with hard gates

DimensionMetricGate or score
HonestyFabricated sources or quotes (programmatic)Hard gate: must be zero
CorrectnessJudge faithfulness and accuracy against reference notesScore
CoverageShare of sub-questions answeredScore
CalibrationAre "Confirmed" facts actually right more often than "Single-source" ones?Score

SafetyFollowed instructions hidden in a web page?Hard gate

Hard gates are never averaged away. A version that is 10% better on average but fabricated one source is rejected. Averages hide exactly the failures that destroy trust.

12.5 Principle five: be statistically honest

Agent runs are noisy: the same agent on the same task can pass once and fail the next time. One improved run proves nothing. So:

  • Run every eval task at least 3 times per version and report the pass rate, not one result.
  • Compare versions on the same tasks, run at the same time, so a website change does not look like an agent change.
  • Accept an improvement only when the gap is larger than the run-to-run noise you have measured.
  • Regression gate: a new version may not drop in any category (for example "trap tasks" or "comparisons") beyond a set threshold, even if the total improves.

12.6 Principle six: diagnose by trace, fix one thing at a time

A score says that something failed. The trace says why. This is where Day 1's observability pays off: every search, page, decision and model call is recorded. Each failure gets one root-cause tag from a fixed taxonomy:

TagMeaningTypical repair
search.bad_querySearches never found the right pagesPrompt: query strategy; more varied queries
read.shallowRight page opened but the key passage missedUse find_on_page; larger page text limit
synthesis.unsupportedClaim not backed by any source readStricter claim ledger rule; programmatic check
coverage.missed_subquestionPart of the question ignoredExplicit decomposition and a checklist before writing
stop.too_early / stop.too_lateStopping rule wrongAdjust stopping rule or step budget
tool.failurePage blocked, timeout, interactive siteBetter tool, or the Browser Use fallback
injection.followedObeyed text inside a web pagePrompt rule plus a safety test; treat as critical

Aggregating tags across the suite tells you where to invest: if 40% of failures are read.shallow, improving the search prompt is wasted effort. Repairs are tried in order of cost and risk: prompt first, then tool choice and budget, then model, and only last new tools (which need a sandbox). Change one thing per version, so the scoreboard can tell you which change helped.

12.7 How to read and evaluate results: a routine

  1. Gates first. Any fabricated source, injection or budget breach? If yes, stop: that version is rejected, whatever else it scores.
  2. Compare with the champion on the same tasks: per category, not just the total.
  3. Check the noise. Is the difference bigger than the variation between repeated runs?
  4. Read the worst five traces in full in the Control Room: the prompt, every tool call, the report. Numbers tell you where; traces tell you why.
  5. Tag the root cause of each failure and look at the distribution of tags.
  6. Write down one hypothesis: "the agent stops before checking a second source because the stopping rule only counts sub-questions".
  7. Make one change, run the full suite with repeats, and let the gate decide.
  8. Turn new failures into eval tasks, so they can never silently return.

12.8 Where the edge comes from

  • The eval suite is the moat. Prompts can be copied; a suite of hundreds of hard, realistic tasks built from real failures cannot. It grows every time something goes wrong.
  • Trap tasks reveal character. Nonexistent studies, conflicting sources, outdated pages, paywalls and pages with hidden instructions show what an agent does under pressure. Most agents are never tested on them.
  • Optimise the frontier, not one number. Track quality against cost per task. A Haiku agent at 95% of Sonnet's quality for 5% of the cost is often the winning product.
  • Close the loop with reality. Once VoyagerOne is used for real questions, add a simple rating per report. Every bad rating becomes a candidate eval task.
  • Evaluate the builder too. The final question is not "is VoyagerOne good?" but "does ForgeOne reliably produce good agents?" Measure how many build rounds it needs to pass the suite, and how often its repairs actually help.
