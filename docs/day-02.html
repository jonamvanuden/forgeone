ForgeOne, Day 2: Architecture

Saturday 21 November 2026, afternoon. How ForgeOne is organised as a long-lived product, why, and where every responsibility lives.

What changed on Day 2

  • ForgeOne became an installable product: one package, src/forgeone, organised by capability, with a forgeone command.
  • Factory and product are separated. Agents no longer live inside ForgeOne. VoyagerOne has its own repository, and ForgeOne publishes each build there on a branch you approve by merging.
  • Evaluation is now the core of the codebase: an eval suite format, a trace model, programmatic checks with hard gates, scorecards and a promotion gate, all tested.
  • The database schema is versioned with migrations, and has tables ready for eval results.
  • The Control Room got a professional violet design, cost tracking in dollars, a pricing fix, a phone layout and this documents page.

1Why restructure

At the end of Day 1, ForgeOne was a handful of Python files in the root of the repository: one file for the graph, one for logging, one for the database, a dashboard folder and a goal folder. That works for a prototype, but not for a product that will grow for years. Three problems would have hit us soon:

  • No place for new capabilities. The runtime, browser tools, judges and a registry of agent versions had no obvious home, so they would have ended up mixed into existing files.
  • The factory and its products were mixed. The VoyagerOne goal and its eval suite lived inside ForgeOne, so every agent would have bloated the factory's repository and history.
  • Hard to verify. Without a package structure and tests, every change risked breaking something unnoticed.

The fix follows the standard for long-lived Python products: a src layout (code in src/forgeone, installed with pip install -e .), one sub-package per capability, explicit rules about which package may use which, and tests that run without an API key or network.

3Dependency rules

Structure only helps if it is kept. These rules are written in ARCHITECTURE.md and several are enforced in code:

  1. spec, llm, config and observability depend on nothing else in ForgeOne (apart from config). They are the foundation.
  2. builder, runtime and evals use the foundation, never each other's internals. The builder will talk to evals only through its public functions.
  3. control_room only reads from the database. It never imports the builder or runtime, so the dashboard can never start or change anything.
  4. The builder never reads an eval suite. Suites live in the agent repository and are loaded only by evals. An agent factory that sees its own exam learns to pass the exam instead of doing the job.
  5. ForgeOne writes only inside an agent repository's agent/ folder, always through AgentRepo.publish, which refuses anything else.
  6. Every database change is a new numbered migration; applied migrations are never edited.
  7. Prompts are files, not strings in code, so every prompt change shows up in a diff.

4Factory and product: agent repositories

ForgeOne is the factory; VoyagerOne is a product it builds. Products have their own lifecycle, history, owners and deployments, so each agent lives in its own git repository. ForgeOne keeps only a list of the agents it manages in agents.yaml.

The registry

# agents.yaml in the ForgeOne root
agents:
  voyagerone:
    path: ../VoyagerOne                                        # checkout next to ForgeOne
    remote: git@github-voyagerone:jonamvanuden/VoyagerOne.git  # SSH alias with its own deploy key
    branch: main

Publishing: how a new version arrives

  • Default, --publish branch: a new branch forgeone/<run-id> with one commit authored by "ForgeOne", pushed to GitHub. You read the diff and merge it: merging is the approval. Your main is never touched by the builder.
  • --publish main commits straight to main (for quick iteration). --publish none leaves the repository alone.
  • If the new spec is identical to the one on main, nothing is published and nothing fails. A fresh BUILD.md alone is not a new version.

Safety rules, enforced in code and covered by tests

RuleWhy
Before a build, the agent repo must be a clean checkout of its base branch; ForgeOne pulls it firstBuilds start from the reviewed state, and the check runs before any tokens are spent
Publish writes only paths under agent/; staging anything else aborts the commitThe builder can never change the goal or its own exam
On any error the repository is reset to exactly how it was, and the branch removedA failed build never leaves half-written files behind
Separate deploy key per repository (github-forgeone, github-voyagerone)A key for one repository can never write to another

New agents

forgeone agent init <name> --path ../<Name> creates a new agent repository from templates: manifest, goal, a starter eval suite with one trap task, agent/ and a README explaining the ownership rules. VoyagerOne itself was created with this command.

6The evaluation architecture

Day 1 described the feedback loop as a plan. Day 2 gives it a home in code: src/forgeone/evals. A result flows through five stages:

The eval suite

Each agent's suite is a YAML file in its own repository (evals/suite.yaml). A case has a stable id, a category, the task, the checks to run, reference notes for the judge, and optionally expect_not_found for trap tasks or a cost budget. The suite has a version hash: results are only compared on the same version, so changing a case never silently mixes old and new numbers. VoyagerOne starts with 10 cases across 7 categories: factual, comparison, recency, trap, conflicting, navigation and safety.

The checks

CheckGateCatches
cited_urls_were_openedhardFabricated sources: a URL in the report that the agent never opened
quotes_found_on_pageshardInvented quotes: quoted sentences not found on any page read
admits_not_foundhardTrap tasks answered as if the non-existent thing were real
within_step_budget, within_cost_budgethardRunaway loops and cost explosions
has_sources, write_report_once, no_run_errorsoftFormat and process errors

forgeone eval checks lists them all. New checks are one function with a decorator, @check("name", hard=True), and suites refer to them by name.

Scorecard and gate

  • Scorecard: pass rate per run, pass^k (share of cases passed in every repeat), pass rate per category, average judge scores, failure-tag counts, average cost, and the list of hard failures.
  • Gate (champion vs challenger): any hard failure rejects; any category that drops more than 10 percentage points rejects; otherwise promote if pass^k improves, or if quality is equal and cost is lower.
  • Judge rubric for research reports (judges/rubrics/research_report.md): faithfulness, completeness and reasoning on an anchored 1, 3, 5 scale, evidence required for every score, plus the failure-tag list from Day 1.

7The store and migrations

The database schema is now versioned. Each change is a numbered SQL file in src/forgeone/store/migrations/; a table schema_migrations records which have run; forgeone db migrate applies the rest, each in its own transaction. Docker runs all migrations automatically when a new database is created.

MigrationContents
001_initialruns, events, llm_calls, decisions, artifacts, dashboard views (Day 1)
002_evalseval_runs (agent version, suite version, scorecard, gate decision) and eval_results (per case and repeat: checks, judge scores, failure tags, cost, link to the trace)

Migration 001 is written so it can run on a database that already has those tables, so existing installations migrate in place. This was tested on a copy holding real data: 22 runs and 43 model calls before, the same after.

8Configuration and the command line

All settings live in config.py and come from the environment (.env, template in .env.example). The project root is found automatically, or set with FORGEONE_HOME.

forgeone build --agent voyagerone [--publish branch|main|none]
forgeone agent list | status <name> | init <name> --path ../<Name>
forgeone eval validate --agent voyagerone
forgeone eval checks
forgeone db migrate | status | backfill
forgeone control-room [--port 8501]
pytest -q                     # 39 tests, no API key or network needed

The old commands, python -m forgeone.graph and python -m forgeone.store status, still work.

9The Control Room

  • Design: deep violet sidebar, light workspace, white panels, Plus Jakarta Sans; passed builds show violet in the build strips.
  • Overview: weekly numbers with change against last week, builds and spend per day, goals, recent activity, model usage by cost, step performance.
  • Cost in dollars on every level, from llm/pricing.py. A bug was fixed: model names reported with a date suffix (claude-sonnet-5-5-20260928) were counted as free. They are now priced, and any model without a known price is shown as a warning instead of being treated as $0.
  • Phones: a bottom tab bar, single-column panels and a full-screen model-call panel below 820 pixels.
  • Project docs: these documents, readable in the app and as PDF; any other file placed in docs/ appears automatically with a download button.

10Server changes

One-time steps after pulling Day 2:

cd ~/ForgeOne && source .venv/bin/activate && git pull
pip install -e ".[dev]"                                   # installs the package and the forgeone command
sed -i 's#dashboard.server:app#forgeone.control_room.server:app#' \
    /etc/systemd/system/forgeone-dashboard.service
systemctl daemon-reload && systemctl restart forgeone-dashboard
docker compose up -d                                      # migrations folder is now mounted
forgeone db migrate

# VoyagerOne: its own deploy key and checkout next to ForgeOne
ssh-keygen -t ed25519 -f ~/.ssh/voyagerone -N "" -C "diskreta18-voyagerone"
#   add ~/.ssh/voyagerone.pub to VoyagerOne → Settings → Deploy keys, with write access
#   add Host github-voyagerone to ~/.ssh/config (IdentityFile ~/.ssh/voyagerone)
cd ~ && git clone git@github-voyagerone:jonamvanuden/VoyagerOne.git
forgeone agent status voyagerone

Day to day, a change from GitHub is deployed with git pull && pip install -e . -q && systemctl restart forgeone-dashboard; docs/OPERATIONS.md has the full cheat sheet.
